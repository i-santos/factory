# Reusable Factory Project Model

This document defines the durable local model shared by the CLI and GUI. One factory is one filesystem folder/project.

## Folder Shape

```text
factory-project/
├── .factory/
│   ├── circuits/
│   ├── machines/
│   ├── automations/
│   ├── sectors/
│   ├── templates/
│   ├── runtime/
│   │   └── runtime-kernel.md
│   ├── runs/
│   └── triangulation/
```

## Circuit

A circuit is a reusable agent runtime unit.

Minimum fields:

```json
{
  "id": "normalize-intake",
  "name": "Normalize Intake",
  "program": ".factory/circuits/normalize-intake/program.md",
  "runtimeKernel": ".factory/runtime/runtime-kernel.md",
  "inputSchema": null,
  "outputSchema": null,
  "description": ""
}
```

Invariants:
- every circuit has exactly one program
- every circuit loads a runtime kernel
- circuit programs must follow the kernel contract
- circuits may call tools or spawn subagents only when the program says so

## Machine

A machine is an ordered set of circuits.

Minimum fields:

```json
{
  "id": "process-package",
  "name": "Process Package",
  "circuits": [
    { "circuit": "define-work", "input": "automation.input" },
    { "circuit": "plan-work", "input": "previous.output" },
    { "circuit": "implement-work", "input": "previous.output" }
  ],
  "description": ""
}
```

Invariants:
- machine circuit order is explicit
- the orchestrator runs circuits serially
- a machine may contain one circuit or many circuits
- output handoff must be configured or default to previous circuit output

## Automation

An automation is an ordered workflow of machines.

Minimum fields:

```json
{
  "id": "process-package",
  "name": "Process Package",
  "machines": [
    { "machine": "triage-package" },
    { "machine": "execute-package" },
    { "machine": "package-release-review" }
  ],
  "description": ""
}
```

Invariants:
- automations reference machines, not sectors
- the orchestrator runs machines serially in the first version
- automation `next` behavior is configured, not inferred from prompt prose

## Sector

A sector is organization-only metadata.

Minimum fields:

```json
{
  "id": "delivery",
  "name": "Delivery",
  "machines": ["process-package"],
  "circuits": [],
  "description": ""
}
```

Invariants:
- sectors do not constrain execution
- sectors can group machines, circuits, or templates for navigation
- automations may link machines across sectors

## Template

A template is an exportable factory definition.

Minimum fields:

```json
{
  "id": "software-delivery-factory",
  "name": "Software Delivery Factory",
  "circuits": [],
  "machines": [],
  "automations": [],
  "sectors": [],
  "runtime": {},
  "triangulation": {}
}
```

Invariants:
- templates must be importable into a new folder
- imported pieces must validate before execution
- templates should preserve IDs or provide deterministic remapping

## Run State

Runs are durable execution records.

Minimum fields:

```json
{
  "runId": "run_...",
  "targetType": "automation|machine|circuit",
  "targetId": "process-package",
  "status": "running|succeeded|blocked|failed",
  "startedAt": "",
  "finishedAt": null,
  "steps": []
}
```

Run state is generated by the orchestrator. It is not reusable template definition.

## Validation Rules

A factory is valid when:

- every machine circuit reference exists
- every automation machine reference exists
- every sector reference exists or is ignored as display-only metadata
- every circuit program exists
- every circuit runtime kernel exists
- every circuit program conforms to the kernel contract
- template imports pass validation before execution

## CLI Surface

Initial command families:

```text
factory circuit create|list|show|validate
factory machine create|list|show|validate|run
factory automation create|list|show|validate|run
factory sector create|list|show
factory template export|import
factory validate
```

The GUI must use the same model and validation rules.
